# NirapodClick

Local-first scam message checker. Pure-Dart rule engine scores a pasted SMS /
WhatsApp / email against known patterns (URL shorteners, IP hosts, urgency,
credential requests, bKash/Nagad impersonation, APK install prompts, …) and
returns a color-coded verdict plus the matched signals. Each scan is saved to
Firestore under the user's account for later review.

## Risk verdicts

The rule engine produces one of four tiers. The colour and headline are
intentional — the app reserves red for `CRITICAL` only.

| Tier      | Score    | Colour | Headline                                   |
|-----------|----------|--------|---------------------------------------------|
| `low`     | 0..14    | green  | Looks safe                                 |
| `medium`  | 15..34   | amber  | Suspicious — review before acting          |
| `high`    | 35..59   | orange | High risk — likely scam                    |
| `critical`| 60..100  | red    | Critical — do not act on this              |

## Production deployment

### 1. Use a separate Firebase project

Never run the dev project in production. Create a second Firebase project
(e.g. `nirapodclick-prod`) and configure it:

```powershell
flutterfire configure --project=nirapodclick-prod --platforms=android,web
```

This regenerates `lib/firebase_options.dart`, `firebase.json`, and the
platform config files to point at the prod project.

### 2. Enable only what you need in the prod console

- **Authentication → Sign-in method → Email/Password → Enable**
- **Firestore → Create database → pick region, start in production mode**

### 3. Deploy the rules (don't leave test mode on!)

```powershell
firebase use --add            # select nirapodclick-prod
firebase deploy --only firestore:rules
firebase deploy --only firestore:indexes
```

The shipped `firestore.rules` allow:

- a signed-in user to read/create their own `users/{uid}/checks/*`
- no updates, no deletes (v1 is append-only — easy to relax later)
- field-level validation (sizes, types, allowed enum values)
- everything else is **denied by default**

### 4. Android release build

```powershell
flutter build appbundle --release
```

Make sure `android/app/google-services.json` came from `flutterfire configure`
against the **prod** project, not the dev one.

### 5. Web release build

```powershell
flutter build web --release
firebase deploy --only hosting
```

### 6. App icon

Two separate PNGs are required — text in a launcher icon becomes illegible at small sizes, so the launcher version is icon-only while the full wordmark lives on the splash and about pages.

| Asset                      | Used for                                  | Notes                            |
|----------------------------|-------------------------------------------|----------------------------------|
| `assets/icon_launcher.png` | Android launcher, iOS app icon, adaptive  | **No text.** Just shield+check.  |
| `assets/logo_full.png`     | Splash, login hero, about page, web hero  | Full wordmark + Bangla tagline.  |

Generate the icon-only version (≥1024×1024 PNG), drop it at `assets/icon_launcher.png`, then:

```powershell
dart run flutter_launcher_icons
```

It will resize into every `mipmap-*/ic_launcher.png`, write the adaptive-icon foreground XML, and write iOS `AppIcon` assets. The AndroidManifest already points at `@mipmap/ic_launcher` and `@mipmap/ic_launcher_round`.

### 7. Env-switch cheatsheet

|| What                              | Dev                          | Prod                                |
||-----------------------------------|------------------------------|-------------------------------------|
|| `firebase_options.dart`           | from dev project             | regenerate with `flutterfire configure --project=nirapodclick-prod` |
|| Firestore mode                    | test mode (30-day expiry)    | **production rules** (deploy ours)  |
|| API keys                          | dev project                  | prod project (locked by API restrictions) |
|| Android `applicationId`            | `com.example.nirapodclick`   | your real package name              |

### 8. CI guardrails

Before each release, run:

```powershell
flutter analyze
flutter test
firebase emulators:exec --only firestore "node firestore.rules.test.js"
```

A red light on any of these should block the release tag.

## Reference data collections (manual seeding)

Two collections are **read by all users** but only writable from privileged environments. They follow the same fail-soft pattern in the client (4-second timeout, returns `[]` on offline / permission-denied / timeout).

### `scam_patterns/{ruleId}` — rule engine

See `lib/data/default_scam_rules.dart` for the full schema. Summary:

```jsonc
{
  "id": "msg-bkash-pin-en-bn-v1",
  "category": "message",                  // "message" | "url" | "phone"
  "lang": "en-bn",                        // or "en" / "bn"
  "weight": 35,                           // 0-100 contribution to risk score
  "patterns": ["share your bkash pin", "bikash pin দিন"],
  "titleEn": "BKash PIN request",
  "titleBn": "বিকাশ পিন চাওয়া",
  "reasonEn": "No legitimate agent will ever ask for your PIN.",
  "reasonBn": "কোনো বৈধ প্রতিনিধি কখনো আপনার পিন চাইবে না।",
  "actionEn": "Never share your PIN. Hang up.",
  "actionBn": "পিন কখনো শেয়ার করবেন না। কল কেটে দিন।",
  "version": 1,
  "active": true
}
```

To deploy rules, paste documents into the Firebase Console under `scam_patterns/`. The client will pick them up on next refresh (or app restart).

### `admin_alerts/{alertId}` — official safety alerts

Admins (UIDs listed in `lib/core/auth/admin_uids.dart`) can compose and preview alerts from inside the app under **Profile → Admin → Safety alerts**. Because Firestore rules deny client writes to this collection (any unauthenticated user could otherwise forge "official" warnings), v1 publishes through the Firebase Console. The admin screen prepares a draft, copies the JSON, and you paste it into the Console to ship.

```jsonc
{
  "titleEn": "New wave of bKash PIN phishing calls",
  "titleBn": "বিকাশ পিন ফিশিং কলের নতুন ঢেউ",
  "bodyEn":  "Scammers are impersonating bKash agents and asking for your PIN. bKash will never call you for your PIN.",
  "bodyBn":  "প্রতারকরা বিকাশ প্রতিনিধি সেজে আপনার পিন চাইছে। বিকাশ কখনো ফোনে পিন চায় না।",
  "severity": "warning",                  // "info" | "warning" | "critical"
  "active": true,
  "version": 1,
  "updatedAt": <firestore-timestamp>
}
```

Publishing workflow:

1. Open the app as an admin, go to **Profile → Admin → Safety alerts → Publish alert**.
2. Fill the form, preview the card, tap **Prepare draft** — JSON is on the clipboard.
3. Firebase Console → Firestore → `admin_alerts` → **Add document** → paste → publish.
4. All clients refresh within a few seconds (or on next app foreground).

To retire an alert, flip `active: false` in the Console. The client filters on `active == true` server-side.

### Future: write from inside the app

A Cloud Function (Blaze tier) reading `kAdminUids` will replace the clipboard step. Until then, the rule "client writes to `admin_alerts` are denied" is the security floor — do not weaken it in `firestore.rules`.

## A note on the rule engine

Each rule lives in its own class in `lib/features/checker/data/rule_engine.dart`
and has a unit test. To add a new pattern:

1. Implement a new `Rule` (typically 5–15 lines).
2. Add it to `_defaultRules`.
3. Add a fixture to `test/fixtures/sample_messages.dart`.
4. `flutter test` — done.

If you change a rule's *weight* or a bucketing threshold, the fixture-pinning
tests will fail and you can decide whether the new behavior is intentional.

Bangla-script scam patterns are covered by adding the Bangla term to the
relevant `_phrases` list (e.g. `বিকাশ` in `_BdImpersonationRule`). The
fixture tests run in both languages, so an English-only change that breaks
Bangla detection will be caught.
